# Skeptic

Simplify the current implementation after development work is complete.

Remove unnecessary concepts, layers, state, files, abstractions, and indirection while preserving intended behavior. Make high-confidence improvements directly rather than only reporting them.

The goal is not the fewest lines. The goal is the smallest clear implementation that satisfies the current requirements.

## Scope

Start with:

```bash
git status --short
git diff HEAD
```

Inspect relevant untracked files as well.

If the user specifies a branch, commit, directory, or file set, use that scope instead.

Focus on the current changes. Read surrounding code, references, tests, types, and configuration only when needed to understand or safely simplify them.

Do not turn the task into a repository-wide cleanup.

If there are no changes and no reliable user-provided scope, stop and report that there is nothing to simplify.

## Priorities

Apply these in order:

1. Preserve correctness, validation, authorization, and data integrity.
2. Preserve intentional observable behavior.
3. Reduce cognitive load and unnecessary concepts.
4. Follow existing project conventions and reuse appropriate existing code.
5. Keep the final diff focused and reviewable.

Preserve public APIs, externally used signatures, database and transaction behavior, side effects, event ordering, async semantics, user-visible output, accessibility, and supported edge cases.

Be especially conservative around authentication, billing, migrations, jobs, webhooks, shared libraries, public exports, generated files, concurrency, caches, and framework conventions.

Search references before changing or deleting shared code.

## Simplification Rules

Challenge code introduced or changed in the current implementation, especially:

* abstractions, wrappers, factories, interfaces, services, repositories, hooks, providers, or files used only once;
* speculative options, extension points, generic types, and configuration for requirements that do not exist;
* duplicated or derivable state, synchronization effects, unnecessary context, memoization, refs, and caches;
* pass-through functions, one-use helpers, excessive file fragmentation, deep nesting, and scattered control flow;
* duplicated logic, dead code, unused exports, redundant fallbacks, defensive branches, logging, and error handling;
* comments that explain obvious code instead of non-obvious constraints or reasons;
* clearly duplicated queries, parsing, API calls, or other meaningful runtime work.

Prefer, in order:

1. Delete unnecessary code.
2. Inline unnecessary indirection.
3. Reuse a clear existing project implementation.
4. Keep straightforward logic local.
5. Extract a small helper when it makes current code easier to understand.
6. Introduce an abstraction only when multiple current call sites clearly become simpler.

Ask whether a concept can simply not exist.

Do not replace one unnecessary abstraction with another. Small, obvious duplication can be better than a generic abstraction that couples unrelated code.

## Constraints

* Do not change architecture, add features, or prepare for hypothetical requirements.
* Do not rename or reformat unrelated code.
* Do not add dependencies unless explicitly requested.
* Do not add caching, concurrency, configuration, or extension points as part of cleanup.
* Do not weaken validation, tests, error handling, authorization, or type safety.
* Do not use `any`, ignore directives, unsafe assertions, disabled checks, or broader ignore rules to make verification pass.
* Do not stage, commit, push, or modify unrelated files.
* Do not force reuse when it creates awkward coupling.
* Do not make subjective style changes.
* Do not change code when behavior cannot be confidently preserved.

It is valid to conclude that the implementation is already close to the simplest reasonable solution.

## Workflow

1. Understand the complete diff and its intended behavior.
2. Identify a small number of high-confidence simplifications.
3. Apply the smallest coherent edits that produce a clear net improvement.
4. Review the resulting diff for accidental behavior changes or unrelated churn.
5. Run targeted tests or checks, followed by the relevant existing project check when appropriate.
6. Revert any cleanup that is not clearly simpler, safer, or easier to understand.

Stop when the current implementation is reasonably simple. Do not continue searching for work merely because more code exists.

## Final Response

Keep the response concise.

### Simplified

* Meaningful changes made

### Kept as-is

* Important items left unchanged because they were risky, unclear, unrelated, or not a clear improvement
* Omit this section when empty

### Verification

* Commands run and their results
* Checks that could not be run
* Pre-existing or unrelated failures

If no meaningful improvements were needed, say:

> No meaningful simplification was needed. The implementation is already close to the simplest reasonable solution.
